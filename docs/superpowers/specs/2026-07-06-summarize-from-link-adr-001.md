# ADR-001：网页总结采用「真·agentic 工具调用循环」而非确定性管线

- 日期：2026-07-06
- 状态：已采纳（Accepted）
- 关联：`docs/superpowers/plans/2026-07-06-summarize-from-link.md`、`docs/superpowers/specs/2026-07-06-summarize-from-link-adr-002.md`、`CONTEXT.md`

## 背景

「网页总结」需要把用户粘贴的一条链接变成一份草稿（标题 + 总结 + 建议标签 + 源链接）。这件事本质上可拆成三步：抓页面、抽正文、调一次 LLM 出总结。

最直接的实现是**确定性管线**：`httpx 拉页面 → trafilatura 抽正文 → 一次 LLM 调用 → 草稿`。固定顺序、单次 LLM 调用、确定性、好测、便宜。这也是设计访谈中给出的**默认推荐**。

但产品意图是「后端实现一个 agent 来**识别**网页」——希望处理过程能根据拿到的页面**自适应**（抽取结果为空时换策略、判断页面形态等），而不是一条写死的流水线。因此需要在「确定性管线」与「真·agentic 工具调用循环」之间做取舍。

## 决策

采用 **真·agentic 工具调用循环**：后端手写一个 tool-calling 循环（httpx 直连 OpenAI 兼容端点，无框架），给 LLM 暴露工具 `fetch_page` / `extract_main_text`，以 LLM 调用 `submit_draft(title, summary, suggested_tags)` 作为**终止**（同时拿到强类型的结构化输出，免去脆弱的 JSON 解析）。

- 工具集**最小**：`fetch_page`（含 SSRF 校验，见 ADR-002）+ `extract_main_text` + `submit_draft`（终答）。v1 不给 web 搜索、不给链接发现/跟随、不给无头浏览器——这些都可日后作为新工具加入，不必改架构。
- 循环**有硬上限**：最大迭代次数、墙钟超时、输入 token 预算，任一触顶即中止（路由返回 504），杜绝烧钱/死循环。
- 终止靠 `submit_draft` 工具调用：LLM 主动产出强类型草稿即结束；这比「让 LLM 吐 JSON 然后我们解析」更可靠。

## 备选方案

### 方案 B：确定性管线（fetch + 抽文 + 一次 LLM 调用）

固定三步、单次 LLM 调用。

- 优点：确定性、与现有 `wiki_publish_service` 的薄服务风格一致、`monkeypatch` 即可单测、最便宜最快。
- 缺点：不能自适应页面形态（抽取空了也只能硬总结、无法中途换策略）。**被产品意图明确否决**——用户要的是「agent 识别网页」，不是写死的流水线。

### 方案 C：上 agent 框架（LangChain / LangGraph 等）

用现成框架的 tool-calling / agent 抽象。

- 优点：电池齐全，少写循环骨架。
- 缺点：本仓库现有服务全是「标准库 + httpx、薄、可 `monkeypatch` 单测」风格；框架是**单一最大、最异质、快变**的依赖，且 agent 框架以难做确定性单测著称。引入它将打破现有测试范式。**否决**。

### 方案 D：官方 OpenAI/Anthropic SDK 的工具调用

用官方 SDK 的 function-calling 能力，少手写循环。

- 优点：比框架轻。
- 缺点：仍是仓库目前不用的依赖；且端点是 OpenAI**兼容**（非官方），SDK 的 OpenAI 特有假设可能在兼容端点上踩坑。直连 `/v1/chat/completions` 最可移植。**否决**。

## 后果

- **正面**：
  - 真正符合「agent 识别网页」的产品意图，能自适应页面形态。
  - 手写循环（约 50 行）透明、可注入模拟 LLM 做确定性单测，与现有测试范式兼容。
  - `submit_draft` 工具即终止，顺带拿到强类型结构化草稿。
  - 工具集最小化，v1 风险可控；日后加工具（搜索/链接/无头浏览器）不必改架构。
- **负面 / 风险**：
  - 相比管线：**非确定性**（同样的 URL 两次结果可能不同）、单测更费劲（需注入脚本化模拟 LLM）、单请求多次 LLM 调用 → **更贵更慢**。
  - 依赖端点 + 模型支持 function-calling 并返回 `tool_calls`；若模型不支持，整个方案走不通（这是硬前提）。
  - 多次外抓放大 SSRF 面 → 必须配 ADR-002 的防护。
- **缓释**：硬上限（迭代/超时/token）封死最坏情况；`fetch_page` 的 SSRF 校验在工具内部、每次调用都跑（见 ADR-002）；per-user 内存限流封住跨请求滥用；端点能力在接入时用一次真实调用坐实。

## 备注

本 ADR 的核心价值是记录一次**非显而易见的否决**：确定性管线是更低风险的默认项、却被主动否决，换成了更复杂的 agent。日后若有人问「为什么不直接 fetch+抽文+一次调用」，答案在此——别把它「简化」回管线，除非产品意图变了。
